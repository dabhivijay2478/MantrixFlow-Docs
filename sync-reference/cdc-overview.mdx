Change data capture, or CDC, reads database change logs instead of rereading whole tables. It is the right choice when you need inserts, updates, and deletes with lower latency and stronger fidelity than cursor-based incremental sync can provide.

## What CDC solves

- captures hard deletes without relying on application-level soft-delete logic
- tracks updates even when the app does not maintain a perfect `updated_at`
- reduces repeated full-table reads on busy production systems
- supports lower-latency replication workflows when incremental sync is not enough

## Current product reality

In the current standard workspace UI, self-serve CDC is exposed for **PostgreSQL sources**. The builder includes a dedicated **CDC Setup** tab for PostgreSQL and the documented supported flow stops there.

## How CDC compares to other sync modes

| Mode | Reads from | Best for | Main tradeoff |
| --- | --- | --- | --- |
| Full sync | current table contents | smaller datasets and first validation | re-reads everything |
| Incremental sync | rows newer than a cursor | most production app tables | depends on a trustworthy cursor |
| PostgreSQL CDC | replication or change log | low-latency operational replication | needs database admin setup |

## When teams justify CDC

- order, payment, or fulfillment systems where deletes and fast updates matter
- operational reporting that must stay close to source-of-truth timing
- PostgreSQL tables where application timestamps are incomplete or unreliable
- pipelines that are already proven with incremental sync but now need lower latency or delete handling

## Safe adoption flow

1. Prove the source and destination with a manual run first.
2. Complete the PostgreSQL CDC prerequisites inside the source panel.
3. Verify the CDC status before enabling log-based sync.
4. Run manually and confirm downstream tables behave as expected.
5. Only then schedule production cadence.
