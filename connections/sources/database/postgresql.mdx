PostgreSQL is the first production database source for the Postgres-to-Postgres live release. Use it when MantrixFlow can reach your database through a public Postgres endpoint that is protected by credentials, SSL, and a provider firewall or IP allowlist.

## Connection fields

The PostgreSQL source form asks for:

- `Connection Name`
- `Host`
- `Port`
- `Database`
- `Username`
- `Password`
- `Schema`
- `SSL Mode`

`Port` defaults to `5432`, `Schema` defaults to `public`, and most managed PostgreSQL providers should use `SSL Mode` set to `require` unless your database administrator gives you a stricter mode.

## Network access

For the live release, MantrixFlow supports PostgreSQL sources that are reachable from the MantrixFlow ELT server:

- public endpoint with database firewall/IP allowlist
- public endpoint without provider allowlist, if your provider permits it and credentials are strong
- local or test database only if it is reachable from the ELT server

Private subnet, private-only, VPC-only, VPN-only, and bastion-only databases are planned for a later SSH tunnel or self-hosted agent release.

Use [Private database access](/connections/private-database-access) to copy MantrixFlow's static outbound IP and configure your provider firewall.

## Provider setup

| Provider | What to configure |
| --- | --- |
| AWS RDS / Aurora PostgreSQL | Use a DB endpoint reachable from the internet and add an inbound security group rule for PostgreSQL `5432` from MantrixFlow's `/32`. See [AWS RDS security group guidance](https://docs.aws.amazon.com/AmazonRDS/latest/gettingstartedguide/security-groups.html). |
| GCP Cloud SQL for PostgreSQL | Enable public IP and add MantrixFlow's `/32` under Authorized networks. See [Google Cloud authorized networks](https://cloud.google.com/sql/docs/postgres/authorize-networks). |
| Azure Database for PostgreSQL | Use public access and create a firewall rule where start IP and end IP both equal MantrixFlow's IP. See [Azure firewall rules](https://learn.microsoft.com/en-us/azure/postgresql/security/security-firewall-rules). |
| Supabase | Use the database connection details from the Supabase dashboard. If Network Restrictions are enabled, add MantrixFlow's `/32`. See [Supabase Network Restrictions](https://supabase.com/docs/guides/platform/network-restrictions). |
| Neon | Use the connection string from the Neon Connect modal. If IP Allow is enabled on your plan, add MantrixFlow's IP/CIDR. See [Neon IP Allow](https://neon.com/docs/reference/cli-ip-allow). |
| Aiven for PostgreSQL | Use the service connection details and configure the IP filter to include MantrixFlow's `/32`. See [Aiven access restriction docs](https://aiven.io/docs/platform/howto/restrict-access). |
| DigitalOcean Managed PostgreSQL | Add MantrixFlow's IP as a trusted source for the database cluster. See [DigitalOcean trusted sources](https://docs.digitalocean.com/products/databases/postgresql/how-to/secure/). |
| Render Postgres | Use the external connection details and restrict external access to MantrixFlow's IP if you enable access restrictions. See [Render Postgres networking](https://render.com/docs/databases). |

## Permissions

Create a dedicated source user instead of using an owner or administrator account.

The source user should have:

- `CONNECT` on the database
- `USAGE` on the selected schema
- `SELECT` on the tables or views you want to sync

For incremental sync, choose a stable cursor such as `updated_at`, `modified_at`, or an increasing ID. Add an index on the cursor column for large tables.

## Step by step

1. In your PostgreSQL provider, create the read-only source user.
2. Add MantrixFlow's `/32` to the provider firewall if required.
3. Open **Connections** and click **+ New Connection**.
4. Keep the role set to **Source** and choose **PostgreSQL**.
5. Fill in the host, port, database, username, password, schema, and SSL mode.
6. Click **Test Connection**.
7. Save only after the connection test succeeds.
8. Create a pipeline and validate one table manually before enabling a schedule.

## Troubleshooting

- Connection timeout usually means the provider firewall, public endpoint, or IP allowlist is not configured for MantrixFlow.
- Authentication failure means the host is reachable, but the username, password, or database is wrong.
- Empty table discovery usually means the user lacks schema `USAGE` or table `SELECT`.
- TLS failures usually mean `SSL Mode` should be `require`, `verify-ca`, or `verify-full` for the provider.

For log-based replication, save the source connection first and then use [CDC setup for PostgreSQL](/sync-reference/cdc-postgresql).
