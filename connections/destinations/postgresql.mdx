PostgreSQL is the clearest first destination in the current app because it is easy to test, easy to validate with SQL, and fully aligned with the live destination panel flow.

## Current connection form

The current **PostgreSQL** destination form asks for:

- `Connection Name`
- `Host`
- `Port`
- `Database`
- `Username`
- `Password`
- `Schema`
- `SSL Mode`

- `Port` defaults to `5432`.
- `Schema` defaults to `public` in the connection form.
- You still choose the final destination `Schema` and `Table` in the builder.

## Good first use cases

- analytics tables for BI and reporting
- operational marts that should not read production directly
- clean SQL tables for downstream apps or internal tools

## Before you connect

- Create a dedicated write user for the reporting database.
- Decide which schema MantrixFlow should own, such as `analytics` or `raw`.
- Pick the first target table name before you configure the branch.

## Step by step

1. Open **Connections** and click **+ New Connection**.
2. Set the role to **Destination** and choose **PostgreSQL**.
3. Fill the form with real values, for example:
   - `Connection Name`: `Analytics Postgres`
   - `Host`: `analytics-db.internal.lighthouse.io`
   - `Port`: `5432`
   - `Database`: `warehouse`
   - `Username`: `mf_writer`
   - `Schema`: `analytics`
   - `SSL Mode`: `require`
4. Click **Test Connection** and save the connection after the test succeeds.
5. In the builder's **Destination** panel, configure:
   - `Connection`: `Analytics Postgres`
   - `Schema`: `analytics`
   - `Table`: `orders_live`
   - `Write mode`: `Upsert`
6. Save the pipeline and run one manual sync before enabling a schedule.

## Real-world example

Lighthouse Commerce lands `public.orders` from Neon into `analytics.orders_live` on a dedicated PostgreSQL reporting instance so BI queries never hit production directly.

## Troubleshooting

- If the connection test fails, confirm host reachability, SSL requirements, and whether the user can connect to the database.
- If the run fails at write time, check schema ownership and whether the write user can create or update objects.
- If rows duplicate unexpectedly, inspect the upstream unique identifier and the way the destination table expects upsert behavior.
