In the builder, a branch is a concrete path from the selected source stream to a destination. Each branch can have its own label, transform script, filter logic, destination connection, and schedule behavior.

## What the transform panel controls today

The live transform panel is centered around a Python function:

```python
def transform(record):
    return record
```

From that panel, you can:

- rename the branch so operators know its purpose
- switch the selected source table when needed
- load source-specific example scripts when examples are available
- preview output against sample source rows
- save the script into the pipeline graph

The live transform panel does not expose a separate visual rename, cast, or null-fill UI. Those patterns are implemented directly in `transform(record)`.

## A realistic branching example

A commerce team might branch one `orders` stream two ways:

- **Analytics branch** writes cleaned rows to PostgreSQL in `analytics.orders_live`.
- **Operations branch** writes a narrower customer-service view to MySQL in `ops.order_lookup`.

That pattern keeps one source read while allowing two different SQL destinations to serve different teams.

## Safe transform workflow

1. Pick the source table or resource first so previews use the right record shape.
2. Start with a pass-through script and change one thing at a time.
3. Use **Preview with sample data** after every meaningful edit.
4. Save the transform before running the pipeline.
5. Validate the destination output before turning the schedule on.

## Good use cases for a transform

- standardize enum values such as `paid`, `Paid`, and `PAID`
- derive reporting-friendly columns such as `order_date` or `mrr`
- remove fields that should not leave the source system
- flatten nested SaaS payloads before they reach SQL destinations
- add metadata such as `loaded_from` or `sync_batch_id`

## Filter nodes in the current builder

The builder also includes a dedicated **Filter** node with two modes:

- a Python expression such as `record.get('status') != 'deleted'`
- a SQL `WHERE` clause for source-side filtering patterns

Use the filter node for simple keep-or-drop logic. Use the transform script when you need filtering plus reshaping in one place.

Current limitation: the filter panel is primarily a configuration surface. Treat source preview, transform preview, destination preview, and a manual run as the authoritative validation path.
