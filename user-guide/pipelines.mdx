The pipeline flow in the current app is intentionally split into two stages:

1. create the pipeline shell from **Data Pipelines**
2. finish the operational setup in the builder canvas

That means the builder is where most production decisions actually happen.

## Key routes

- List: `/workspace/data-pipelines`
- Create shell: `/workspace/data-pipelines/new`
- Builder: `/workspace/data-pipelines/[id]/builder`
- Detail page: `/workspace/data-pipelines/[id]`

## Create the pipeline shell

Start with a pipeline name and a source connection. The create page does not ask for every configuration option up front because the builder owns stream selection, transform logic, destination setup, and schedule.

![Create pipeline form](/images/user-guide/ug-new-pipeline-form.png)

## Configure the builder

The builder is the real control room for the pipeline.

- **Source panel** chooses the table or API resource.
- **Transform panel** edits the Python script and branch label.
- **Destination panel** chooses the destination connection, schema, table, preview, and schedule.
- **Action bar** lets you save, run manually, and open schedule or settings.

![Pipeline builder - branches on canvas](/images/user-guide/ug-pipeline-builder-branches.png)

## The recommended first-run sequence

<Steps>
  <Step>

### 1. Select one source table or resource

Start with one high-value object such as `public.orders`, `stripe.customers`, or `github.pull_requests`. This keeps validation focused.

  </Step>
  <Step>

### 2. Keep the first transform simple

Either pass records through unchanged or add one small enrichment field so debugging stays straightforward.

  </Step>
  <Step>

### 3. Configure the destination carefully

Pick the destination connection, confirm the schema and table name, and keep the first write behavior conservative. In current builder releases, **Upsert** is the primary live option.

  </Step>
  <Step>

### 4. Save before you run

Use **Save** in the action bar so the selected stream, transform script, destination, and schedule are persisted.

  </Step>
  <Step>

### 5. Run manually

Use **Run Now** to validate the pipeline with operator attention before you introduce automation.

  </Step>
</Steps>

## Review run history

After the run, open the detail page and inspect **Run History**. This is where you confirm status, row counts, runtime, and whether a pipeline succeeded after a credential or schema change.

![Pipeline detail - run history and warning banner](/images/user-guide/ug-pipeline-detail-runs.png)

## Typical reasons a run fails

- the source or destination connection was edited but not re-tested
- the selected source table no longer exists or permissions were removed
- the transform script returns invalid records
- the destination schema or table name is wrong
- a schedule fired after a credential rotation

## Row actions on the pipeline list

Use the list page for fast operations:

- **Open Builder** to change the graph
- **Run Now** for manual validation
- **Delete** when you intentionally retire the pipeline

![Pipeline row overflow menu](/images/user-guide/ug-pipeline-row-menu.png)

## When to schedule a pipeline

Schedule only after three things are true:

1. the source connection tests cleanly
2. the destination receives the correct shape
3. at least one manual run has succeeded end to end
