## Organizations

An organization is the workspace boundary for connections, pipelines, team members, activity, and schedules. Many teams keep one organization for production and one for staging so credentials and run history stay separate.

## Connections

A connection is a reusable credential set plus connector-specific configuration. Connections live under **Connections** and are created with a role of **Source** or **Destination**.

Examples in the current product:

- a PostgreSQL source connection for an application database
- a Shopify source connection for store data
- a GitHub source connection for one repository
- a PostgreSQL or MySQL destination connection for reporting tables

## Pipelines

A pipeline begins as a lightweight shell created from **Data Pipelines**. The builder is where the operational details are finished: source selection, sync mode, transform script, destination table, and schedule.

## Branches

A branch is a path on the canvas from the selected source stream to a destination. A realistic branching pattern today is:

- Branch A writes cleaned `orders` data to PostgreSQL for analytics.
- Branch B writes a narrower version of the same records to MySQL for an internal application view.

## Sync modes

The app currently supports three read patterns:

- **Full sync** for smaller datasets and first-run validation
- **Incremental sync** for tables or resources with a dependable cursor field
- **CDC** for PostgreSQL sources that complete the in-product CDC setup flow

## Destination behavior

The current destination panel is centered on **Upsert**. Append and Replace are not part of the supported production flow documented here.

## Run history and sync state

Every run stores operational metadata such as status, timing, processed rows, and errors. Incremental and CDC pipelines also maintain sync state so later runs know where to resume.

## Mental model to keep in mind

An organization owns connections, a pipeline shell points to a source connection, the builder turns that shell into one or more branches, and run history tells you whether the configured flow actually worked.
